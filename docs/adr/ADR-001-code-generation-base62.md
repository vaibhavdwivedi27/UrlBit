# ADR 001: Cryptographically Random Base62 Codes vs. Sequential Database IDs

- **Status:** Accepted
- **Deciders:** Backend Architecture Team
- **Date:** 2026-10-24
- **Applies to:** Milestone BE1, BE2, BE8

---

## Context
A URL shortener must map long destination URLs to compact short codes. Two primary code generation paradigms exist:
1. **Sequential/Auto-incrementing IDs encoded to Base62** (e.g. converting `id = 1000` to `g8`).
2. **Cryptographically Random Base62 Strings** generated by a pseudo-random number generator (e.g. `SecureRandom`).

## Decision
Urlbit uses **7-character cryptographically random Base62 codes** (`[0-9A-Za-z]`) generated using `java.security.SecureRandom`. Public codes are completely decoupled from database primary keys. Collisions are handled at insert time using PostgreSQL native `INSERT ... ON CONFLICT (code) DO NOTHING RETURNING id` with bounded retries (up to 3 attempts).

## Rationale & Tradeoffs

### Why Sequential IDs were REJECTED:
1. **Business Enumeration & Competitor Intelligence:** Sequential IDs expose exact link volume and velocity. A competitor could create a link today and tomorrow to calculate exact daily creation volumes.
2. **Link Scraping & Brute-Force Scanning:** Attackers can trivially crawl all short links by incrementing sequential integers (`.../1`, `.../2`, `.../3`), defeating access controls and discovering private links or sensitive query parameters.
3. **Single Point of Coordination:** Sequential generation requires central coordination (e.g. distributed sequences or database sequences) which becomes a write bottleneck under high multi-region concurrency.

### Why Random Base62 was ACCEPTED:
1. **Massive Address Space:** $62^7 \approx 3.52 \text{ trillion}$ unique combinations. At 100 million stored links, collision probability on a single attempt is approximately $\frac{100 \times 10^6}{3.52 \times 10^{12}} \approx 0.0028\%$ (virtually zero).
2. **Decoupled from Database Engine:** No central lock, Snowflake coordinator, or distributed ticket service is required. Workers generate candidates locally and in parallel.
3. **Transactional Safety with `ON CONFLICT DO NOTHING`:**
   Instead of catching a `UniqueViolationException` (which aborts the PostgreSQL transaction and rolls back caller state, such as guest quota increments), we use `INSERT ... ON CONFLICT (code) DO NOTHING RETURNING id`. If `null` is returned, the code was taken and we retry with a new random code while keeping the ongoing transaction valid.

## Consequences
- **Positive:** Immune to enumeration attacks; no business metric leakage; completely safe multi-instance concurrency without coordination.
- **Negative:** Negligible risk of retry overhead under extreme key saturation (mitigated by massive 3.52T key space).
